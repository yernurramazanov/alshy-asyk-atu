# Архитектура Alshy

## 1. Назначение документа

Документ определяет техническую архитектуру игры Alshy и служит руководством для реализации требований из `PRD.md`.

> Статус на 1 октября 2026: дальнейшие разделы описывают целевую архитектуру, включая необязательную облачную синхронизацию. Опубликованная версия реализована на Next.js 16 со статическим экспортом для Vercel, Phaser/Matter и локальным сохранением в `localStorage`. Supabase Auth/Postgres и синхронизация между устройствами **не реализованы**. Фактические возможности и ограничения приведены в `README.md`.

При конфликте документов:

1. правила продукта и объём определяет `PRD.md`;
2. технический способ реализации определяет этот документ;
3. фактическое поведение опубликованной версии должно быть отражено в README.

## 2. Архитектурные цели

- быстро получить полностью работающий игровой раунд;
- обеспечить одинаковую игровую логику на компьютере и телефоне;
- отделить физическую симуляцию от интерфейса и облачных функций;
- описывать испытания данными, а не копировать сцены;
- сохранять игру работоспособной при отказе Supabase;
- обеспечить детерминированный подсчёт результата;
- позволить удалить необязательную функцию без переделки ядра.

## 3. Технологический стек

### 3.1. Клиент

- Vite;
- TypeScript в строгом режиме;
- Phaser;
- Matter Physics, встроенный в Phaser;
- HTML и CSS для экранов меню, профиля и результатов;
- Canvas Phaser для игрового поля.

### 3.2. Данные

- `localStorage` для настроек, обучения и локального прогресса;
- IndexedDB не требуется для первой версии;
- Supabase Auth для профиля;
- Supabase Postgres для результатов и прогресса;
- Row Level Security для ограничения доступа.

### 3.3. Развёртывание

- GitHub как основной репозиторий;
- Vercel как статический хостинг;
- переменные окружения с префиксом `VITE_` только для публичных клиентских параметров;
- секретные серверные ключи в клиенте запрещены.

## 4. Архитектурные решения

### ADR-001 2D вместо 3D

**Решение:** использовать вид сверху или под небольшим псевдоизометрическим углом.

**Причина:** 2D снижает риск проблем с камерой, производительностью, моделями и мобильным управлением. Проверяющие оценивают механику выше сложности графики.

### ADR-002 Phaser и Matter Physics

**Решение:** игровая сцена и физика реализуются в Phaser с Matter.

**Причина:** Matter поддерживает твёрдые тела, массу, трение, упругость, вращение и столкновения сложнее кругов и прямоугольников.

### ADR-003 HTML-интерфейс поверх Canvas

**Решение:** меню, формы и результат реализуются DOM-компонентами, а игровое поле — Canvas.

**Причина:** DOM проще адаптировать, тестировать и сделать доступным с клавиатуры. Игровая симуляция остаётся внутри Phaser.

### ADR-004 Локальная работа прежде облачной

**Решение:** каждый результат сначала записывается локально, затем синхронизируется.

**Причина:** сетевой сбой или ошибка авторизации не должны ломать раунд.

### ADR-005 Конфигурационные испытания

**Решение:** уровни задаются объектами конфигурации.

**Причина:** одна игровая сцена обслуживает все режимы, а различия ограничиваются параметрами и условием победы.

## 5. Общая схема

```text
Пользователь
   |
   v
DOM UI <----> App Store <----> Phaser Game
   |              |                |
   |              |                v
   |              |          Matter Physics
   |              |                |
   |              +<---- Game Events
   |              |
   v              v
Local Repository  Sync Service ----> Supabase
```

### Границы ответственности

- **Phaser Game** рассчитывает игровой мир и отправляет события.
- **DOM UI** показывает меню, HUD, правила, профиль и результат.
- **App Store** хранит состояние текущей сессии, не являясь физическим движком.
- **Repositories** сохраняют прогресс и результаты.
- **Sync Service** объединяет локальные и облачные данные.

## 7. Направление зависимостей

```text
UI ---------> domain <--------- game
                 ^
                 |
data adapters ---+
```

Правила:

- `domain` не импортирует Phaser, DOM или Supabase;
- `game` не обращается напрямую к Supabase;
- сцены не записывают `localStorage` напрямую;
- UI получает данные через store и события;
- адаптеры данных реализуют интерфейсы доменного слоя.

## 8. Доменная модель

### 8.1. Asyk

```ts
type AsykStatus = 'active' | 'outside' | 'scored'

interface AsykState {
  id: string
  status: AsykStatus
  position: { x: number; y: number }
  rotation: number
}
```

Инварианты:

- `scored` является конечным состоянием внутри одного раунда;
- объект с `scored` не участвует в последующих бросках;
- переход к `scored` возможен только через `outside` после разрешения броска.

## 9. Машина состояний раунда

```text
preparing
   |
   v
aiming <------+
   |          |
   v          |
charging      |
   |          |
   v          |
simulating    |
   |          |
   v          |
resolving ----+
   |
   v
completed
```

Переход `resolving → aiming` выполняется, если цель не достигнута и остались броски. Иначе выполняется `resolving → completed`.

Ограничения:

- ввод запуска разрешён только в `aiming` и `charging`;
- в `simulating` повторные клики игнорируются;
- подсчёт выполняется только в `resolving`;
- сохранение результата выполняется один раз при входе в `completed`.

## 10. Физическая модель

### 10.1. Координаты

- игровая логика использует виртуальное поле фиксированного размера;
- Canvas масштабируется под экран без изменения физических координат;
- игровая граница хранится как окружность с центром и радиусом;
- UI не использует экранные пиксели для расчёта очков.

### 10.2. Формы тел

Для первой версии:

- асык — компактный выпуклый многоугольник или составное тело;
- сақа — более крупное и тяжёлое тело того же семейства;
- визуальный спрайт и физическое тело имеют согласованный центр;
- граница круга не является физической стеной, поскольку асыки должны её пересекать.

### 10.3. Параметры

Все параметры находятся в одном конфигурационном файле:

```ts
interface PhysicsTuning {
  sakaMass: number
  asykMass: number
  friction: number
  frictionAir: number
  restitution: number
  minLaunchSpeed: number
  maxLaunchSpeed: number
  sleepSpeedThreshold: number
  settleDurationMs: number
  simulationTimeoutMs: number
}
```

Запрещено распределять числовые коэффициенты по сценам.

### 10.4. Завершение броска

Бросок считается завершённым, когда выполняется одно из условий:

1. скорость и угловая скорость всех активных тел ниже порога в течение `settleDurationMs`;
2. достигнут защитный тайм-аут `simulationTimeoutMs`.

После этого физика ставится на паузу для подсчёта.

### 10.5. Определение выхода

Для каждого активного асыка вычисляется расстояние от центра арены:

```text
distance = sqrt((x - centerX)^2 + (y - centerY)^2)
```

Асык является кандидатом на выбивание, если его физическое тело полностью находится за кругом. Для первой версии проверяется:

```text
distance - boundingRadius > arenaRadius + tolerance
```

`tolerance` компенсирует погрешность физического движка.

### 10.6. Защита от двойного счёта

Алгоритм разрешения:

1. выбрать только асыки со статусом `active`;
2. определить полностью вышедшие тела;
3. перевести их в `outside`;
4. сформировать неизменяемый список идентификаторов;
5. увеличить счёт на длину списка;
6. перевести объекты в `scored`;
7. удалить их физические тела после завершения анимации результата.

## 11. Управление

### 11.1. Единая модель указателя

Мышь и касание преобразуются в единый поток pointer-событий Phaser.

Основная схема:

- начало жеста на сақа;
- перемещение указателя к цели задаёт направление броска;
- длина протягивания задаёт силу;
- отпускание запускает бросок.

На текущем игровом экране нет ползунков, клавиш прицеливания и отдельной кнопки броска: они давали бы несколько конкурирующих способов управления. Касание использует тот же pointer-жест на мобильном устройстве.

### 11.2. Нормализация

- сила ограничивается диапазоном `[0, 1]`;
- мёртвая зона предотвращает случайный слабый бросок;
- направление вычисляется в мировых координатах;
- изменение размера окна во время броска не меняет траекторию.

## 12. Конфигурация испытаний

```ts
interface ChallengeConfig {
  id: string
  title: string
  description: string
  targetScore: number
  maxThrows: number
  requiredHitStreak?: number
  layout: AsykSpawnConfig[]
  physicsOverrides?: Partial<PhysicsTuning>
  unlockRequirement?: {
    challengeId: string
    minScore?: number
    mustWin?: boolean
  }
}
```

Условия:

- конфигурация не содержит исполняемый код из внешнего источника;
- все режимы используют `RoundSystem` и `ScoringSystem`;
- новое испытание должно добавляться без изменения `GameScene`.

## 13. Обратная связь после раунда

`FeedbackSystem` выбирает один совет по приоритету:

1. мало попаданий — предложить скорректировать направление;
2. много попаданий, но мало выбитых — увеличить силу;
3. частые перелёты — уменьшить силу;
4. высокая точность — предложить более сложное испытание;
5. победа — показать улучшение относительно личного рекорда.

Советы формируются локально по фиксированным правилам. AI API для этого не требуется.

## 14. Хранилища

### 14.1. Интерфейсы

```ts
interface ProgressRepository {
  getProgress(): Promise<PlayerProgress>
  saveProgress(progress: PlayerProgress): Promise<void>
}

interface ResultsRepository {
  listResults(limit: number): Promise<GameResult[]>
  saveResult(result: GameResult): Promise<void>
}
```

### 14.2. Локальные ключи

```text
alshy.settings.v1
alshy.progress.v1
alshy.results.v1
alshy.syncQueue.v1
```

Каждая структура содержит номер версии. Повреждённые данные заменяются безопасными значениями по умолчанию без падения приложения.

### 14.3. Стратегия записи

1. завершить раунд;
2. сохранить результат локально;
3. обновить локальный прогресс;
4. поместить операцию в очередь синхронизации;
5. при наличии сессии отправить в Supabase;
6. после успеха отметить запись как `synced`;
7. при ошибке оставить `pending` или `failed` для повторной попытки.

## 15. Supabase

### 15.1. Таблицы

#### profiles

```text
id uuid primary key references auth.users
display_name text not null
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

#### game_results

```text
id uuid primary key
user_id uuid not null references profiles(id)
client_result_id text not null
mode text not null
score integer not null
throws_used integer not null
successful_throws integer not null
accuracy numeric not null
won boolean not null
best_shot integer not null
created_at timestamptz not null
inserted_at timestamptz not null default now()
unique(user_id, client_result_id)
```

#### player_progress

```text
user_id uuid primary key references profiles(id)
unlocked_level integer not null default 1
best_score integer not null default 0
tutorial_completed boolean not null default false
updated_at timestamptz not null default now()
```

### 15.2. RLS

Минимальные политики:

- пользователь читает и обновляет только собственный профиль;
- пользователь читает и записывает только собственные результаты;
- пользователь читает и обновляет только собственный прогресс;
- публичная таблица лидеров, если добавляется, строится через ограниченное представление без email и других персональных данных.

### 15.3. Объединение прогресса

При первом входе на устройстве:

- `bestScore = max(local.bestScore, cloud.bestScore)`;
- `unlockedLevel = max(local.unlockedLevel, cloud.unlockedLevel)`;
- `tutorialCompleted = local || cloud`;
- локальные результаты с уникальным `client_result_id` добавляются в облако;
- облачные результаты не дублируются локально.

## 16. Store приложения

Store содержит только состояние интерфейса и сессии:

```ts
interface AppState {
  route: AppRoute
  auth: AuthState
  settings: Settings
  progress: PlayerProgress
  currentRound?: RoundSummary
  sync: SyncState
}
```

Полные объекты Matter и ссылки на сцены Phaser в store не помещаются.

## 17. События между игрой и UI

Минимальный контракт:

```ts
type GameEvent =
  | { type: 'round:started'; payload: RoundSummary }
  | { type: 'aim:changed'; payload: { angle: number; power: number } }
  | { type: 'shot:released'; payload: { shotNumber: number } }
  | { type: 'shot:resolved'; payload: ShotResult }
  | { type: 'score:changed'; payload: { score: number } }
  | { type: 'round:completed'; payload: GameResult }
  | { type: 'tutorial:step'; payload: { step: number } }
```

События типизированы. Строки событий не создаются произвольно в сценах.

## 18. Обработка ошибок

### 18.1. Классы ошибок

- ошибка загрузки обязательного ресурса;
- ошибка локального сохранения;
- ошибка авторизации;
- ошибка облачной синхронизации;
- тайм-аут физической симуляции;
- некорректная конфигурация испытания.

### 18.2. Поведение

- ошибка облака отображается как неблокирующее уведомление;
- физический тайм-аут принудительно переводит раунд в `resolving`;
- некорректное испытание скрывается из меню и логируется;
- ошибка обязательного ресурса показывает экран повторной загрузки;
- ошибки не выводят пользователю стек вызовов или технические секреты.

## 19. Тестирование

### 19.1. Модульные тесты

Приоритетные функции:

- определение выхода за круг;
- защита от двойного начисления;
- условия победы и поражения;
- расчёт точности;
- открытие испытаний;
- объединение локального и облачного прогресса;
- валидация конфигурации уровня.

### 19.2. Интеграционные тесты

- `aiming → charging → simulating → resolving`;
- успешный бросок обновляет HUD;
- неудачный бросок уменьшает остаток попыток;
- завершение раунда сохраняет один результат;
- рестарт создаёт чистое состояние;
- отказ Supabase не прерывает локальное сохранение.

### 19.3. E2E-сценарии

1. Первый запуск и прохождение обучения.
2. Полный проигранный раунд.
3. Полный выигранный раунд.
4. Перезапуск после результата.
5. Восстановление прогресса после обновления страницы.
6. Мобильный жест броска.
7. Вход и синхронизация между двумя браузерными сессиями.

### 19.4. Ручная физическая проверка

- минимальная сила;
- максимальная сила;
- прямое центральное попадание;
- касательное попадание;
- несколько одновременных столкновений;
- выход асыка ровно на границу;
- вылет нескольких асыков;
- отсутствие движения дольше защитного тайм-аута.

## 20. Производительность

- не создавать физические тела каждый кадр;
- удалять выбитые тела после разрешения броска;
- использовать пул частиц;
- ограничить количество звуков столкновения за кадр;
- не обновлять DOM на каждом физическом тике;
- HUD обновлять только при изменении значения;
- тяжёлые декоративные ресурсы загружать после обязательных.

## 21. Адаптивность

- виртуальное поле сохраняет пропорции;
- на узком экране HUD располагается сверху и снизу, не по бокам;
- минимальный размер интерактивной кнопки — 44 на 44 CSS-пикселя;
- ориентация portrait поддерживается, landscape рекомендуется;
- при смене ориентации активный бросок не перезапускается;
- безопасные отступы учитывают вырезы мобильного экрана.

## 22. Доступность

- DOM-кнопки имеют понятные подписи;
- фокус клавиатуры видим;
- результат сообщается текстом и визуально;
- предусмотрено уменьшение декоративного движения;
- звук отключается без отключения визуальной обратной связи;
- направление и сила доступны альтернативным контролом без drag-жеста.

Приложение должно запускаться без заполненного Supabase при `VITE_ENABLE_CLOUD=false`.

## 24. CI и качество кода

Минимальные проверки перед публикацией:

```text
npm run typecheck
npm run lint
npm run test
npm run build
```

Рекомендуемый pipeline GitHub Actions:

1. установка зависимостей через lock-файл;
2. typecheck;
3. lint;
4. unit tests;
5. production build.

Падение любой проверки блокирует слияние в основную ветку.

## 25. Развёртывание

### 25.1. Окружения

- local — локальная разработка;
- preview — автоматический URL для ветки или pull request;
- production — ссылка для сдачи.

### 25.2. Проверка production

- открыть URL в приватном окне;
- пройти обучение;
- завершить раунд;
- обновить страницу и проверить прогресс;
- проверить мобильный viewport;
- убедиться, что network-запросы не содержат секретов;
- проверить отсутствие ошибок в console;
- сравнить commit опубликованной версии с GitHub.

## 26. Наблюдаемость

В production логируются только необходимые сведения:

- тип ошибки;
- версия приложения;
- режим;
- фаза раунда;
- обезличенный идентификатор сессии.

Не логируются email, токены, содержимое хранилища и точные персональные данные.

## 28. Точки остановки

После каждой фазы должна существовать запускаемая версия.

- после B допустим только внутренний прототип;
- после C существует сдаваемый уровень «Средний»;
- после D существует основной кандидат уровня «Сильный»;
- E добавляется только без ухудшения C и D;
- F не может менять правила или архитектуру ядра без повторного полного теста.

## 29. Запрещённые упрощения

- заранее заданная анимация вместо физики;
- случайное определение выбитых асыков;
- начисление очков в обработчике столкновения до остановки;
- отдельная игровая сцена на каждое испытание;
- прямые запросы к Supabase из игровых объектов;
- обязательная авторизация до начала игры;
- хранение секретного ключа в клиенте;
- блокирование раунда из-за ошибки аналитики или синхронизации;
- визуальный асык, размеры которого не соответствуют физическому телу.

## 30. Техническое определение готовности

Архитектура реализована достаточно для сдачи, если:

- production build воспроизводим из чистого checkout;
- игровая логика отделена от UI и облачных адаптеров;
- состояния раунда имеют однозначные переходы;
- двойное начисление покрыто тестом;
- испытания создаются конфигурацией;
- локальный режим работает без Supabase;
- мобильное управление проверено на реальном устройстве;
- production URL проходит полный раунд без ошибок;
- README соответствует фактической реализации.
